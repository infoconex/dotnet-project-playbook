# Playbook-specific security engineering standards

Security guidance is risk- and system-dependent. Microsoft's [secure development and threat-modeling guidance](https://learn.microsoft.com/en-us/security/engineering/threat-modeling-with-dev-ops), GitHub's [code security documentation](https://docs.github.com/en/code-security), NuGet's [package auditing documentation](https://learn.microsoft.com/en-us/nuget/concepts/auditing-packages), and the [OWASP cheat sheets](https://cheatsheetseries.owasp.org/) are primary technical references. The [security and software supply-chain guide](../security-guidance.md) provides a non-normative application map. This document registers **three distinct playbook obligations** where authoritative guidance leaves implementation and review decisions to the adopting project; it does not mandate a universal security tooling stack.

Interpret **Required**, conditional applicability, and recorded exceptions under [standards governance](../governance/standards.md). Use the [standards catalog](README.md) for permanent identifiers. These standards complement [CI/local parity (STD-002)](engineering-principles.md#std-002), [risk-based diagnostics (STD-008)](csharp.md#std-008), and [external-boundary verification (STD-009)](testing.md#std-009), without redefining their obligations.

## <a name="std-019"></a>STD-019 — Secrets and sensitive-data protection

**Level and applicability:** **Required** when a new or materially changed .NET project, repository workflow, deployment, or integration handles credentials, tokens, keys, connection secrets, personal or otherwise sensitive data, or systems that can expose them. At a minimum, repository contributors must avoid committing live secrets. Detailed data-handling controls depend on the actual data, deployment, trust boundaries, and applicable contractual or regulatory obligations; do not assume a public utility library processes production personal data.

**Purpose and rationale:** Exposure can occur through tracked files, build logs, exception messages, test fixtures, configuration, or overly privileged access. Vendor scanning detects only some patterns and circumstances. The playbook makes **deliberate protection and an exposure response** an explicit obligation rather than treating a green scan as proof of confidentiality. See [OWASP Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html), [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html), and Microsoft's [ASP.NET Core development-secret guidance](https://learn.microsoft.com/en-us/aspnet/core/security/app-secrets).

**Normative expectation:** Keep live credentials and other secrets out of committed source, example configuration, test fixtures, generated artifacts, and diagnostic output. Use access-controlled, deployment-appropriate secret storage or injection for real credentials; limit principals and privileges to the actual need. Identify sensitive data relevant to the project and protect it at applicable input, storage, transit, log, export, and access boundaries. When exposure is suspected or confirmed, contain the exposure, revoke or rotate affected credentials as appropriate, assess impact, and use the repository's established private reporting/incident route. Deleting a committed secret from the current file or rewriting history **does not** invalidate a leaked credential.

**Implementation guidance:** Favor environment-specific protected configuration, managed secret stores, and scoped identities where appropriate. ASP.NET Core user secrets are for local development convenience, **not encrypted production storage**. Keep examples synthetic, redact diagnostics, avoid printing environment variables or tokens in CI, and constrain build/release credentials. Review the repository's existing configuration and incident requirements before selecting new controls. Where a project never processes sensitive business data, document the limited applicability rather than inventing encryption layers or a secret manager. The [practical guide](../security-guidance.md#secrets-sensitive-data-and-response) expands the decision process.

**Verification:** Inspect tracked configuration, samples, log/error paths, tests, build workflow permissions, and relevant secret-injection mechanisms. Record the protection boundary, applicable controls, reviewer, specific evidence, and gaps. If secret scanning or push protection is enabled, inspect its actual enablement, supported pattern coverage, alert handling, and observed results; neither absence of alerts nor presence of a badge proves the repository contains no exposed secrets. For a discovered credential exposure, confirm the required response actions independently of repository cleanup.

**Exceptions and alternatives:** Use synthetic or explicitly non-sensitive test credentials where necessary and ensure they cannot access real environments. Platform-specific stores and compliance mechanisms may differ. A genuine Required-standard exception must identify the exposure scenario, compensating controls, owner, residual risk, and follow-up. It cannot consist solely of disabling detection, suppressing an alert, or declaring a live secret safe because its repository is private.

## <a name="std-020"></a>STD-020 — Dependency vulnerability management

**Level and applicability:** **Required (conditional)** for projects with third-party dependencies, including direct packages and relevant transitive dependencies, build tools, plugins, containers, and other externally supplied components used by the project. A project with no third-party dependencies has no dependency inventory to manage under this standard; reassess if dependencies are added. Select supported auditing mechanisms according to actual NuGet client, project format, package ecosystem, and deployment context, including traditional .NET Framework projects.

**Purpose and rationale:** NuGet and hosting-service advisories provide useful signals but differ by ecosystem, graph visibility, affected versions, and client. A lock file, successful restore, or zero alerts does not prove components are vulnerability-free. The playbook makes review and disposition of actionable risk explicit without prescribing a universal update schedule, a single scanner, or an automatic merge policy. See [NuGet package auditing](https://learn.microsoft.com/en-us/nuget/concepts/auditing-packages) and [GitHub Dependabot alerts](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-alerts).

**Normative expectation:** Maintain an understandable inventory of the dependency inputs material to the project; use applicable vulnerability information to evaluate direct and transitive exposure. Triage relevant findings by actual affected version, exploitability/reachability where assessable, product exposure, severity, and potential impact. Remediate by an appropriate compatible update, removal, replacement, or other effective mitigation; if work is deferred or the risk is accepted, record owner, rationale, compensating controls, review condition, and follow-up. Treat credible high-risk security fixes with urgency appropriate to their consequences, independent of ordinary maintenance-update grouping. Never silently suppress findings or infer an acceptable risk solely from tool silence.

**Implementation guidance:** Prefer NuGetAudit where supported; review the exact direct/transitive scope and warning behavior of the installed SDK/NuGet version. Complement with the applicable dependency graph, advisory service, or other maintained tools when the ecosystem or legacy project format is outside a given tool's coverage. Keep routine compatibility/version updates reviewable and proportionate; distinguish Dependabot **alerts**, **security update PRs**, and **scheduled version update PRs**. Verify package provenance and trusted sources using [build/dependency guidance](../build-dependency-guidance.md) without introducing mandatory Central Package Management, lock files, or package source mapping. See the [practical guide](../security-guidance.md#dependency-security-and-update-handling).

**Verification:** Identify dependency formats and sources, graph coverage, audit tool/client versions, advisory age or refresh point where available, settings, actual output, and triage disposition. Review relevant transitive components and missing ecosystems. Demonstrate the chosen update/mitigation against actual restore, build, and appropriate tests **when executed**, separately from documented intent. An unresolved risk must remain visible as an explicit decision, not a passing security check. Record unavailable private feeds, incompatible tooling, or unverified runtime behavior honestly.

**Exceptions and alternatives:** A justified Required-standard exception may address temporarily unpatchable packages, unsupported legacy clients, or unavailable advisory data with alternative review, containment, owner, residual risk, and reassessment trigger. Unsupported auditing is a coverage gap, **not** exemption from reviewing the dependency risk. A project with no third-party dependencies is conditionally out of scope, not noncompliant. No fixed severity threshold, remediation-day SLA, commercial scanner, or automatic dependency-PR merge is universally mandated.

## <a name="std-021"></a>STD-021 — Security-sensitive change review

**Level and applicability:** **Required (conditional)** for **material** changes affecting authentication or authorization, privileges, trust boundaries, handling of sensitive data, externally exposed behavior, cryptography, or CI/build/deployment mechanisms that can gain privileged access or affect trusted artifacts. Small internal refactors without a material change to a relevant risk boundary do not automatically trigger a separate security review. Assess the *effect of the change*, not just filenames or labels.

**Purpose and rationale:** Automated analysis, dependency advisories, and integration tests surface different classes of defects; none substitutes for evaluating a changed security assumption. The playbook requires a proportionate, traceable review when consequences warrant it, drawing on [Microsoft threat modeling with DevOps](https://learn.microsoft.com/en-us/security/engineering/threat-modeling-with-dev-ops) and the [OWASP Application Security Verification Standard](https://asvs.owasp.org/).

**Normative expectation:** Before accepting a material security-sensitive change, record a risk-proportionate review of the changed boundary, assets, threat/abuse or failure cases, proposed protections, and relevant verification evidence or explicit gaps. Identify the responsible reviewer or review owner, unresolved risks, and disposition. Review how authorization fails, how sensitive data can escape, and how least privilege and recovery apply **where relevant**. For high-impact or non-obvious changes, use a more structured threat model or equivalent analysis; select security testing techniques based on actual exposure. Record a reviewed exception if this Required review cannot be completed. A green CI build or static-analysis result alone is not this review.

**Implementation guidance:** Reuse existing PR review and architecture/security records; a short focused security section can suffice for low-to-moderate material risk. A structured data-flow/trust-boundary analysis, misuse cases, stakeholder review, or a specialist consultation may suit higher risk. SAST reviews source patterns; SCA evaluates dependencies; DAST probes a running application and may be irrelevant to pure libraries. Select actual tests for affected boundaries, including [STD-009](testing.md#std-009) where its independent trigger is met. For privileged workflows, verify permissions and the handling of untrusted contributions. See [practical review examples](../security-guidance.md#security-sensitive-change-review).

**Verification:** Inspect the proposed change and preserved risk assessment; confirm that the identified threats, controls, reviewer, verification results, outstanding unknowns, and risk decisions match its actual effects. Document the exact tests/analyses executed and tools/environments used, rather than claiming a threat-model exercise or DAST run that was merely proposed. Security review does not establish that production deployment, exploitation resistance, or every runtime path has been tested.

**Exceptions and alternatives:** The review form and depth may differ by team, deployment, and legacy context. For emergencies, record the expedited decision, approver/owner, temporary containment, residual risk, and post-change follow-up. A narrowly scoped Required-standard exception is possible through governance but cannot be replaced with an unreviewed “security not applicable” assertion when the material trigger is present. No universal formal threat-model document, pen test, DAST environment, or paid security product is required for every PR.

## Scope of this issue

These are **standards documentation**, not an implementation of controls in any consuming repository. The [practical guidance](../security-guidance.md) illustrates tooling choices, evidence types, and appropriate alternatives. This issue does **not** enable scanning, modify GitHub security settings, add workflow permissions or CI jobs, change `SECURITY.md`, introduce dependencies, provide executable validators, run threat models or tests, or audit the security of this repository or any example. Adoption and compliance require separate inspection and observed evidence in the specific project.
