# STD-018 — Event-Driven Architecture

The playbook follows Microsoft's [Event-Driven Architecture style](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/event-driven), [publisher-subscriber pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/publisher-subscriber), [asynchronous messaging choices](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/messaging), and relevant .NET domain/integration event guidance by default. This standard makes one independent, **conditionally Recommended** playbook obligation assessable: **when material interactions are event-mediated, the owners must make consequential event contracts, processing guarantees, and failure/recovery responsibilities deliberate and reviewable**.

The unique subject is the **event-mediated interaction across independently failing or independently evolving producer/consumer processing**, even when both run inside one deployment. It is **not** a mandate to adopt event-driven architecture, a reinvention of DDD domain ownership, or another definition of microservice autonomy.

This document alone is the normative authority for STD-018. [Standards governance](../governance/standards.md) controls levels and exceptions; the [catalog](README.md) indexes this standard; [on-demand guidance](../event-driven-guidance.md) provides selection matrices, failure scenarios, and non-normative implementation examples. Microsoft's primary guidance remains the reference for documented platform and messaging behavior.

## <a name="std-018"></a>Purpose, level, and applicability

**Level: Recommended (conditional).** Consider event-driven communication only where demonstrated requirements benefit from independent consumers, loose temporal coupling, reliable asynchronous work, workload buffering, integration, high-volume streams, or durable event histories—and the added contract, eventual-outcome, observability, failure-recovery, security, and operating costs are acceptable.

**Adoption trigger:** Apply the adopted-style expectations below to **material event-mediated producer/consumer flows** in a new or materially changed system where asynchronous timing, delivery, independent consumer execution, or replay/recovery materially affects business correctness, compatibility, availability, or operations. The trigger is about behavior, not whether an application references a mediator, raises a domain event, contains multiple modules, or uses a particular technology. An explicitly synchronous, in-transaction domain-event reaction with no independent delivery/recovery semantics ordinarily remains within STD-014's domain/transaction guidance rather than triggering this standard by itself.

A pure library, small CRUD application, single-project utility, modular monolith, or microservice using straightforward synchronous calls can legitimately omit event-driven architecture. Event-driven communication may be adopted within one deployable application and does not require microservices, a distributed deployment, or a message broker. Existing projects can adopt a limited flow incrementally while preserving public contracts and behavior.

If an existing system claims event-driven architecture but evidence is incomplete, report observed behavior, intended design, and unresolved risks separately. A documented simpler alternative is valid under the Recommended level and is not noncompliance with a Required standard. Independently Required principles—including TDD, SOLID, business-policy independence, and conditional representative external-adapter verification—still apply.

## Normative expectations when adopted

1. **Justify the communication mechanism and its scope.** Identify the consequential business or technical outcome, producer, consumers, and specific need for asynchronous/event-mediated collaboration. Compare appropriate simpler direct calls, in-process operations, synchronous HTTP/gRPC, local transaction coordination, or background work before selecting durable queues, pub/sub, streams, or event-sourced state. Choose topology and infrastructure proportionately. Do not assume a mediator, broker, one handler per event, one queue/topic per capability, a separate database, CQRS, event sourcing, or microservices.

2. **Specify event meaning and authoritative ownership.** Distinguish a command requesting work from an event stating an occurrence, a local domain event from a public integration event, and a notification from state transfer. Identify the owner of each material published fact and the consumers' legitimate independent responsibilities. For event contracts that cross ownership or independent evolution boundaries, document the semantics of event type, stable identity, relevant business identifiers, correlation/causation, creation/commit/publication timestamps as needed, and immutable published meaning. Do not expose mutable internal domain entities or persistence representations merely to avoid a translation contract. Not every domain event needs publication.

3. **Control compatibility of published event contracts.** Define consequential schema fields, optionality, validation, ownership, supported versions, consumer expectations, rollout/migration, and handling of unknown or obsolete versions. Account for retained/replayed messages and different consumer upgrade schedules when relevant. Prefer compatible evolution and deliberately manage breaking changes rather than forcing simultaneous consumer deployments. A shared domain assembly, code generation, schema registry, CloudEvents envelope, JSON, Avro, or Protobuf is not universally required. Preserve existing externally published contracts unless a deliberately reviewed migration is authorized.

4. **Make publication timing and consistency consequences explicit.** Determine which state changes must succeed atomically, when a fact becomes authoritative, what happens if a publisher emits an event before its business transaction commits and the transaction then rolls back, and what happens if the commit succeeds but external publication fails. Keep critical invariants inside an appropriate atomic boundary when possible. If losing a corresponding event has consequential business effects, choose and verify an appropriate durable publication/reconciliation approach; a transactional outbox with a reliable relay is one option, not a universal mandate. Where separate transactions are justified, describe tolerable staleness, partial completion, recovery, and user-visible pending outcomes. Do not claim atomicity between a local database transaction and an external broker without actual mechanism and evidence.

5. **Define delivery separately from business-effect guarantees.** For consequential consumers, identify the actual at-most-once, at-least-once, or constrained exactly-once transport semantics, expected duplicate/redelivery behavior, concurrency, ordering scope (including partition-local limits), retry/backoff, poison/dead-letter handling, message expiration/retention, replay, backpressure, and extended-outage recovery as applicable. Where duplicate execution could cause harm, ensure effects are idempotent or consistently deduplicated at the authoritative effect boundary, including relevant persistence and external effects. Broker-side duplicate-send filtering or a transport-level exactly-once claim must not be represented as proof of exactly-once business effects. Explicitly handle delayed, obsolete, missing-reference, and already-processed messages where their consequences matter.

6. **Coordinate multi-step business processes without hiding irreversibility.** For materially consequential workflows spanning independently committed operations, identify who owns completion, the stage/outcome states, failure boundaries, retry/compensation or reconciliation paths, and how partial progress is detected. Use direct owner operations and local transactions where they can satisfy actual consistency requirements; consider process managers, sagas, durable workflow state, and human intervention only when justified. Explain when compensation cannot reverse an irreversible external action; do not promise all-or-nothing outcomes solely from a sequence of events.

7. **Protect messaging trust and data boundaries.** Identify producer and consumer identities, permitted publishing/subscription operations, application authorization for resulting business actions, tenant separation, payload minimization, necessary encryption/integrity, credential handling, replay exposure, retention/deletion, audit logging, and sensitive telemetry according to risk. Being on an internal network or authenticated to a broker does not by itself authorize a consumer to mutate business state. Apply existing security and privacy obligations regardless of deployment style. No identity provider, broker, encryption product, or observability platform is mandated here.

8. **Assign operational and recovery ownership.** For material asynchronous workflows, state who can detect and respond to publication failures, stalled or delayed business outcomes, retry exhaustion, dead letters, consumer lag/backlog, replay/reprocessing, invalid versions, and required reconciliation. Select appropriate correlation, diagnostics, technical and business completion signals, retention controls, incident actions, and capacity/storage monitoring. Distinguish successful delivery/acknowledgment from completion of the intended business outcome. Do not require a dedicated team, formal SLO, particular instrumentation library, or round-the-clock operations for every trivial handler.

9. **Verify actual claims proportionately.** Review semantic ownership, contracts, source dependencies, publication timing, delivery configuration, authorization, and recovery responsibilities. Use independent behavior tests for meaningful domain rules and producer/consumer decisions; where material external adapters are changed, follow the independently conditional **Required STD-009** with representative actual dependencies or appropriately provider-validated contracts. For consequential atomicity, deduplication, broker ordering, expiry, replay, security, workflow recovery, deployment or observability claims, collect corresponding representative tests or observed running-system evidence; otherwise mark the property unverified. Record revision, platform/toolchain, relevant implementation and dependency versions, commands/results, reviewed failure cases, exceptions, and unknowns. Compilation, static configuration, mocks, and isolated unit tests do not prove end-to-end delivery, security, or resilience.

These expectations address **significant adopted event-mediated interactions**. They do not establish a fixed checklist per trivial event, an infrastructure quota, or a mandatory test suite for every possible message failure.

| [STD-014 — DDD](ddd.md#std-014) | Independently Recommended model fidelity, aggregate invariants, bounded contexts, and domain-event meaning. A domain event is not automatically an integration contract. |

Single-project, traditional layered/N-tier, Hexagonal, Clean, DDD, modular monolith, Vertical Slice, and Microservices Architecture can coexist with event-mediated behavior, but no one implies adoption of another. Event-driven architecture does not require event sourcing, CQRS, separate databases, eventual consistency for all operations, or a saga.

## Proportional verification and evidence limits

| Evidence | Can establish | Cannot establish by itself |
| --- | --- | --- |
| Source/configuration/contract review | Declared event types, ownership, dependencies, configured retry/retention and intended trust boundaries | Actual production delivery, successful end-to-end processing, enforced authorization or recovery |
| Independent domain, publisher and consumer tests | Meaningful logic, allowed/rejected behavior, deserialization and simulated duplicate/out-of-order decisions | Real broker delivery, database atomicity, deployed trust/isolation or throughput |
| Schema and consumer/provider contract verification | Checked compatibility for the versions, payloads and implementations actually exercised | Every future consumer version or all replayed historical events |
| Representative database/broker/infrastructure integration | Observed transaction, publication, redelivery, concurrency, authorization, lock/expiry and replay behavior under tested configuration | All network partitions, regional incidents or every operational scenario |
| Deployed workflow, security and operational probes | Observed end-to-end business outcomes, recovery, telemetry and operational capability in specified environment | Untested disaster recovery, load limits or global exactly-once external effects |

Select evidence by business risk, not every possible row. When real dependencies or deployment environments are inaccessible, record limitations and any necessary STD-009 exception under its separate governance. Documentation examples in the playbook are **not compiled, executed, or production-verified** merely because they are published.

## Alternatives, exceptions, and incremental adoption

- **Use a simpler mechanism** for immediate decisions, local atomic invariants, simple CRUD, tightly coordinated small applications, or limited operational capacity. A justified alternative satisfies the Recommended decision process; an omission is not a Required-standard exception.
- **Adopt a narrower asynchronous scope** for one workload, integration or consumer while leaving other paths synchronous. In-process background work can be legitimate, but its shutdown, restart and loss semantics must match requirements; concurrency alone does not imply durable work.
- **Choose durable queues, pub/sub or streams** only for their particular reliability, distribution, fan-out or replay needs. A broker alone does not prove that publication, processing, and business effects are reliable.
- **Choose outbox, inbox, deduplication, schema registry, durable coordinator, partitioning or an event store** when actual consequences justify the machinery. Describe residual failure modes and operational cost.
- **Preserve .NET compatibility.** Choose constructs and dependencies supported by the actual C# language version, runtime, OS, project format and build tooling. Modern SDK-style .NET and traditional .NET Framework (including legacy non-SDK projects) may adopt the same semantic guidance with different infrastructure or implementation details. Do not assume package compatibility, hosted-worker APIs or multi-OS behavior without applicable authoritative support and project-specific verification.
- **Incrementally modernize.** Characterize existing public contracts, producer/consumer behavior and transaction guarantees before replacing direct calls with events or changing an existing event version. Maintain appropriate dual-read/dual-write or migration strategies only when their risks and operational ownership are understood.

A material departure **within an adopted STD-018 scope** should be explained and reviewed: identify the specific expectation, practical alternative, consequences, evidence, and follow-up. This does not convert every Optional pattern into a required one.
