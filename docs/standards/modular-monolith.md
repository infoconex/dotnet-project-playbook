# STD-015 — Modular Monolith Architecture

The playbook follows [Microsoft's .NET architecture guidance](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/architectural-principles) by default. This standard makes a distinct, conditional architectural choice independently assessable: **when a modular monolith is adopted, meaningful business-capability modules must preserve intentional ownership, encapsulation, and controlled collaboration while sharing an application deployment**. A folder named `Modules` or a collection of class libraries does not establish these properties.

The [standards catalog](README.md) registers this identifier. The [on-demand modular monolith guide](../modular-monolith-guidance.md) supplies optional C# examples, decision tables, and review scenarios; it is not another normative authority. [Standards governance](../governance/standards.md) controls applicability and alternatives.

## <a name="std-015"></a>Purpose, level, and applicability

**Level: Recommended (conditional).** Prefer this architecture when a new or materially changed application has **meaningful, independently evolving business capabilities** whose ownership, change coupling, integration, or testing would benefit from recognizable module boundaries within one deployable application. Material signals include competing business responsibilities, recurring cross-feature change ripple, independent business ownership, or uncontrolled internal/data access. A monolith's size, number of files or projects, anticipated microservices, or architectural fashion alone does not trigger adoption.

A cohesive pure class library, straightforward CRUD application, small service, or technical orchestration component may use a documented simpler arrangement. A complex application may also choose an alternative if its actual ownership and constraints justify that choice. This Recommendation does **not** make modularity compulsory for every project. When a scope **claims to adopt modular monolith architecture**, assess its meaningful module boundaries against the expectations below; merely organizing source by feature does not establish adoption.

One application deployment may contain one or several compiled production projects. These responsibilities apply to both modern SDK-style .NET and traditional .NET Framework using the actual supported runtime, C# version, project format, and tooling. An existing monolith may improve one affected boundary at a time without a wholesale rewrite, schema split, or commitment to eventually extracting microservices.

## Normative expectations when adopted

1. **Identify cohesive business-capability modules and ownership.** State each material module's business responsibility and which business behavior, important invariants, and data it owns. Boundaries should reflect meaningful change and collaboration, not arbitrary folder counts, technical layers, team names, or one class per module. An owner denotes an accountable business responsibility; a dedicated team or repository is not required. Reassess a boundary if apparently separate modules repeatedly require one another's private behavior or coordinated changes.
2. **Expose intentional module-facing contracts and encapsulate internals.** When another module or host consumes a capability, define a small, stable, discoverable public surface for that interaction. A suitable public facade, operation type, or interface may be used; **an explicit C# interface is not required for every module, service, or operation** by this standard. Cross-module consumers must not invoke another module's private implementation classes, internal repositories, persistence models, or mutable state as a shortcut around its published capability. Do not expose vendor-specific infrastructure solely because it is convenient for the caller. A module with no cross-module consumer need not invent a service interface.
3. **Control module dependency direction and shared responsibilities.** Record meaningful dependencies between modules and keep **implementation-level module dependencies acyclic**, including cases where a single assembly hides the graph. Depend on another module's approved contract, not its internals. Evaluate mutual callbacks, events, and runtime call chains for semantic cycles even if the project-reference graph compiles. Reassign misplaced behavior, use a suitable outer coordinator, or introduce narrowly shared concepts where necessary. A shared abstraction must express genuinely common meaning or capability, not become a universal shared domain model, shared DAL, or uncontrolled service hub.
4. **Preserve business and data ownership.** A module's mutations must enforce its own business decisions and invariants. Other modules must not independently write module-owned records through direct SQL, an ORM context, a repository, or shared mutable objects in ways that bypass the owner. A **shared physical database and shared database schema are permitted**; no database/schema/table-per-module rule is imposed. Prefer owner-controlled contracts for cross-module business reads. Explicit reporting queries, projections, or other controlled read-only paths may be justified where authorization, consistency, ownership, performance, and schema coupling are understood. Cross-module foreign keys or direct read joins need deliberate coupling review, not automatic prohibition.
5. **Choose appropriate consistency and communication.** Prefer direct synchronous **in-process** collaboration through approved module surfaces when the caller needs an immediate outcome or coordinated transaction. Local atomic transactions crossing owned operations may be appropriate when the actual persistence mechanism supports the required guarantee; coordinate through module-owned operations rather than bypassing their invariants. Identify which module owns the outcome, who coordinates the transaction, and how failures and concurrency affect consistency. Use mediation, domain/application events, or asynchronous messaging only where specific collaboration, fan-out, or temporal-decoupling needs justify them. When events are used, define relevant synchronous versus after-commit behavior, ordering, failure propagation, duplicate handling, and delivery guarantees. A broker, outbox, distributed transaction, CQRS, event sourcing, or eventual consistency is **not** required merely because modules interact.
6. **Compose modules deliberately.** Keep material module registration, initialization, dependency wiring, and lifetime responsibilities discoverable. An application host/composition root may reference contracts and implementations to connect modules. Manual construction or supported dependency injection is acceptable; a separate service container per module is not mandatory. Avoid hidden global service locators and accidental lifetime coupling. A shared host may manage startup and shutdown even though modules own their business behavior.
7. **Keep logical and physical boundaries distinct.** One production project may contain multiple logical modules, including feature-oriented directories. Multiple assemblies can provide useful compiler-enforced references and assembly-scoped `internal` encapsulation when their benefits justify additional maintenance. In a **single assembly**, C# `internal` does not protect one module's directory or namespace from another, and a namespace or folder is not an enforced boundary. Use proportional source-level review or suitable focused checks where project separation is absent. [STD-003](engineering-principles.md#std-003) keeps separate compiled projects **Optional**; no fixed project count or assembly per module is required.

These expectations define an **adopted architectural style**, not a universal prohibition of direct calls, shared databases, synchronous transactions, or concrete C# classes. No application becomes a distributed system merely because it exposes a module contract.

## Proportional verification and evidence limitations

For materially created or changed adopted modules, use evidence appropriate to the risk:

1. **Map ownership and meaningful interactions.** Identify the business capability, actual owner, public operations, internal implementation, shared abstractions, dependency consumers, and relevant data mutation paths. Check that intended boundaries represent actual use cases and change pressures.
2. **Review source and objective dependency edges.** Inspect calls, imports, references, reflection or service-location shortcuts, and cross-module data access. Where separate assemblies are used, inspect project references or focused architecture checks. Where one assembly contains modules, supplement with source/semantic review. Check that implementation-level dependencies do not cycle. Neither a green build nor a clean reference graph proves encapsulation.
3. **Test meaningful module behavior and collaboration.** Exercise representative allowed and rejected business operations through the public module surface; test significant caller/owner interactions and relevant error propagation. Verify module-owned invariants remain protected through all material mutation paths. Follow STD-001 for applicable executable changes without a mandatory test for trivial forwarding.
4. **Verify material data and lifecycle behavior.** Where changes affect cross-module transaction handling, concurrency, read-model consistency, or startup/lifetime wiring, select targeted integration or composition tests that exercise the actual mechanism. Apply STD-009 to significant external-adapter behavior. A unit test using an in-memory fake cannot prove SQL transactions, event durability, or production registration.
5. **Report actual evidence and limits.** Record the reviewed revision, concrete paths, executed commands/results, supported toolchain/environment, meaningful scenarios, known deviations, and unverified properties. Distinguish architectural guidance and manual review from implemented and observed behavior. There is no required universal analyzer, messaging test harness, prescribed number of module tests, or new CI gate.

The [on-demand guide](../modular-monolith-guidance.md#level-3--review-verify-and-modernize) provides optional examples of each kind of evidence. Its snippets are **illustrative**, not compiled reference applications or tests by virtue of being published.

## Alternatives, deviations, and incremental modernization

- **Choose a simpler shape** for cohesive libraries, straightforward CRUD or technical applications, and existing systems without demonstrated capability boundary benefits. Explain the tradeoff at the architecture decision or assessment point; omitting a Recommended style is not a violation of independently Required standards.
- **Adopt incrementally** around a meaningful changed business capability in existing .NET Framework or modern .NET applications. Characterize behavior, preserve public contracts and supported project formats, and control data access one mutation path at a time. Do not presume SDK-style migration, multiple assemblies, new technology, or independent deployment is part of module extraction.
- **Describe adopted-style deviations honestly.** If a module is labeled independent but another module imports its implementation, mutates its tables, or creates implementation dependency cycles, do not claim the adopted boundary complies. Identify the reason, the least-disruptive mitigation, affected behavior, residual risks, actual evidence, and appropriate follow-up. An independently Required STD-010/011/001/009 violation follows that standard's reviewed-exception process.
- **Choose physical or distributed separation only for a concrete requirement.** Stronger project isolation can help enforce contracts; independent deployments are a distinct choice with reliability and operational implications. A modular monolith can remain the appropriate long-term architecture.

The conditional module-level obligation and proportional alternatives above are the playbook's distinct, owner-approved decision.
