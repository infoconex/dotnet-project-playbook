# Engineering standards catalog

This index identifies engineering practices that the .NET Project Playbook can use when proposing a new project's foundation or assessing an existing repository. The linked standard, not its index entry, owns the normative expectation. The [standards governance](../governance/standards.md) defines obligation levels, conditional applicability, exceptions, and identifier rules.

The catalog is **an initial subset**, not a complete set of .NET engineering standards or an automated compliance checker. Subsequent issues will add detailed guidance and further standards without changing the identities already assigned. For C# conventions already established by Microsoft, consult the [Microsoft C# guidance map](../csharp-guidance.md) directly; the C# standards below capture only deliberate playbook obligations or choices.

## Applying the catalog to a project

Determine the project's purpose, project type, target framework, supported operating systems, and known constraints. Inspect an existing repository's actual files and decisions before reaching a conclusion. The project's type alone does not establish compliance or justify adding extra projects and configuration files.

| Project context | How to interpret the initial standards |
| --- | --- |
| Class library | Apply SOLID, business-policy independence, and TDD to applicable new behavior and fixes; a pure library need not adopt Hexagonal, Clean, or Vertical Slice Architecture or physical layers. STD-009 does not apply without a significant external-adapter boundary. |
| Command-line application | Assess the same practices against its actual dependencies and test surfaces; introduce CI/local parity guidance when CI is present. |
| Web API | Assess foundation practices and applicable security standards against actual authentication, authorization, sensitive-data, hosting, and deployment boundaries. |
| Worker | Assess applicable engineering practices without assuming the application needs web presentation or a prescribed project graph. |
| Modern SDK-style .NET | Use the project's actual SDK and target framework to select meaningful verification; do not infer untested OS support from the project format. |
| Traditional .NET Framework | Retain applicable engineering principles while accounting for legacy project/tooling constraints and Windows-only runtime behavior. |

These are **applicability notes**, not an exhaustive or profile-specific standards matrix. A Recommended standard (including conditional DDD) may have a justified alternative, an Optional standard need not be adopted, and a conditional standard cannot be treated as a failure when its trigger is absent. If evidence is missing, report the assessment as unknown rather than assuming compliance or a defect. For C# projects, use the [Microsoft C# guidance map](../csharp-guidance.md) to identify the applicable official recommendations before applying the additional playbook obligations.

## Where additional standards belong

The [build and dependency configuration guide](../build-dependency-guidance.md) explains conditional SDK/MSBuild/NuGet configuration, legacy compatibility, dependency locking, source trust, and verification without assigning a separate build-configuration standard or redefining [CI/local parity (STD-002)](engineering-principles.md#std-002), [EditorConfig (STD-007)](csharp.md#std-007), or [diagnostic enforcement (STD-008)](csharp.md#std-008). It is non-normative guidance, not an additional registered standard.

Group related standards in topic-oriented Markdown documents as those standards are approved. Each independently assessable practice receives one permanent global identifier. Categories can change, but identifiers cannot; individual EditorConfig keys and other low-level configuration settings ordinarily remain implementation details of a practice.

The [testing guide](../testing-guidance.md) expands practical test selection without creating an ID for every technique. The [dependency-direction guide](../dependency-direction-guidance.md) illustrates practical policy boundaries without creating a second Required definition. The [Hexagonal guide](../hexagonal-guidance.md) offers optional C# examples and boundary-test explanations without redefining STD-012. The [Clean Architecture guide](../clean-guidance.md) shows a protected Application Core, composition, and simpler alternatives without redefining STD-013. The [single-project architecture guide](../single-project-guidance.md) applies existing standards and Microsoft's guidance to small libraries and applications without introducing a single-project standard. The [traditional layered and N-tier guide](../layered-n-tier-guidance.md) distinguishes logical responsibilities from physical deployment tiers without introducing a separate layered standard. Separately, [STD-014](ddd.md#std-014) makes domain-model fidelity a conditional Recommended choice, and the [on-demand DDD guide](../ddd-guidance.md) offers strategic/tactical examples and simpler alternatives. [STD-015](modular-monolith.md#std-015) independently governs adopted module ownership and collaboration; the [modular-monolith guide](../modular-monolith-guidance.md) illustrates proportionate implementation and verification without redefining it. [STD-016](vertical-slice.md#std-016) governs feature/use-case cohesion and change locality when adopted; the [Vertical Slice guide](../vertical-slice-guidance.md) illustrates proportionate organization and tests without redefining it. [STD-017](microservices.md#std-017) governs conditional independent service deployment and operational autonomy; the [Microservices guide](../microservices-guidance.md) compares deployment choices and risk-proportional evidence without redefining STD-017. [STD-018](event-driven.md#std-018) addresses materially significant event-mediated contract, processing, and recovery responsibilities independently of service deployment; its [on-demand Event-Driven guide](../event-driven-guidance.md) compares communication alternatives and failure consequences without redefining it. [STD-019–STD-021](security.md) define the new security protection, dependency-risk, and review obligations; their [on-demand guide](../security-guidance.md) compares risk-based tools and evidence without mandating a scanner suite. Future topic guidance will further address compatibility, requirements, and verification. Do not create placeholder files merely to reserve these topics or IDs. Existing Microsoft guidance should be linked rather than redefined in new playbook standards unless a deliberate deviation or stronger obligation is approved.

For interactive project setup and read-only existing-repository assessment, follow the single [start-here guide](../../start-here.md). Reusable consumer templates, executable checks, and comprehensive domain guidance are not yet available through this catalog.
