# Playbook-specific automated testing standards

Microsoft's [.NET testing overview](https://learn.microsoft.com/en-us/dotnet/core/testing/), [unit-testing practices](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-best-practices), and relevant framework-specific integration guidance are the primary technical references. The [testing guidance map](../testing-guidance.md) explains their application to modern SDK-style and traditional .NET Framework projects. This document adds **one deliberate playbook obligation** beyond that general guidance. It does not restate the Required [TDD standard (STD-001)](engineering-principles.md#std-001) or assign IDs to individual testing techniques.

The [standards governance](../governance/standards.md) defines Required, Recommended, and Optional obligations and the treatment of exceptions. The [catalog](README.md) preserves permanent identifiers.

## <a name="std-009"></a>STD-009 — Representative external-boundary verification

**Level and applicability:** **Required**, conditionally, for newly introduced or materially changed adapter behavior involving a real external dependency **when incorrect behavior presents significant correctness, compatibility, data-integrity, security, or reliability risk**. Evaluate the actual dependency, change, and consequences; the mere presence of an interface or adapter does not trigger a test for every method. A pure library without a relevant external boundary is outside this standard.

**Purpose and rationale:** An isolated test with a fake repository, network client, or database does not prove that an actual dependency follows the assumed behavior. Microsoft's [ASP.NET Core integration guidance](https://learn.microsoft.com/en-us/aspnet/core/test/integration-tests) and [EF Core testing strategy](https://learn.microsoft.com/en-us/ef/core/testing/choosing-a-testing-strategy) explain when integration evidence matters and why providers can behave differently. The playbook deliberately strengthens that advice for **materially significant changes** without imposing universal end-to-end testing.

**Normative expectation:** Obtain focused **executable verification** of consequential boundary behavior using a representative real dependency implementation or an appropriately validated consumer/provider contract. Select verification whose fidelity matches the risk; verify both successful behavior and important failure behavior when relevant. Clearly distinguish what was exercised against a real implementation, what a provider-validated contract establishes, and what only a test double simulates. Neither an unvalidated mock contract nor an isolated test-double assertion is evidence that the real dependency behaves correctly.

**Implementation guidance:** Examples include SQL dialect/query and transaction behavior against the intended database provider, serialization or file-format compatibility against representative data, HTTP protocol/error handling against a suitable service test environment, or message delivery semantics against an appropriate broker. Keep test data isolated, arrange deterministic setup and cleanup, and separate environment-specific suites where necessary. Contract tests can provide meaningful compatibility evidence when their expectations are checked against the provider; they do not automatically establish deployment, operational, or full end-to-end behavior. Use risk to choose representative paths, not an arbitrary number of integration tests.

**Verification:** Review the adapter behavior and risk that triggered this standard; the chosen real implementation or validated contract and its version/configuration; exact tests executed, outcomes, and environment; and relevant failure cases. Report absent, skipped, or inaccessible verification as a gap, not a pass. A green unit-test suite alone cannot establish compliance with STD-009. Where CI executes only part of the matrix, identify the evidence supplied by other environments and its limits; [STD-002](engineering-principles.md#std-002) remains the separate guidance for repository-controlled CI/local checks.

**Exceptions and alternatives:** When representative execution is genuinely impractical—for example, an external provider offers no safe test environment or a platform is unavailable—request a reviewed and recorded Required-standard exception identifying the concrete limitation, alternative evidence, residual risk, and appropriate follow-up. A validated contract, recorded manual probe, or deferred environment test may reduce uncertainty but must not be represented as full real-integration verification. An existing adapter unchanged by the work does not automatically need retrospective testing solely because this standard was introduced; reassess when its behavior is materially changed.

## Scope of this issue

This is documentation-only. The [practical guide](../testing-guidance.md) provides selection criteria, examples, and version-aware tooling references; it is not a consumer-ready test suite. No test framework, infrastructure container, runner, reporting extension, CI workflow, coverage threshold, or custom validation tool is mandated or delivered by this document. Compliance requires relevant observed evidence in the adopting repository, not merely the presence of this standard.
