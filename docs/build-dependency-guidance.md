# Build, dependency, and repository configuration guidance

This guide helps developers choose proportionate .NET SDK, MSBuild, NuGet, and repository settings for **new projects** and **existing repositories**. Prefer platform-provided mechanisms and the fewest files that satisfy real compatibility, security, reproducibility, and maintenance needs. It is **non-normative**: the [standards catalog](standards/README.md) and linked standards own playbook obligations. Microsoft's and NuGet's documentation owns tool behavior; examples here do not establish that an uninspected repository was built or tested.

**References reviewed:** November 15, 2026 (America/Los_Angeles). Recheck behavior against the actual SDK, NuGet client, MSBuild, Visual Studio/Build Tools, project system, OS, target framework, and package sources. This issue does not deliver a configuration template, build script, NuGet package, CI workflow, or runtime compatibility test.

## Choose the configuration before choosing files

First establish whether the repository contains SDK-style projects, traditional non-SDK .NET Framework projects, or both. Inspect project and solution files, actual package references, supported operating systems, release artifacts, available tools, and CI. Decide which outcomes matter: shared defaults, coordinated versions, controlled restore, private feeds, analyzers, or reproducible release evidence. Only then select configuration mechanisms.

For a new small library, a compatible project file and the [required new-C#-project EditorConfig (STD-007)](standards/csharp.md#std-007) may be enough. A complex multi-project service with private packages and audited CI may justify additional central files. For an existing repository, preserve functioning conventions unless there is evidence of a problem or a worthwhile improvement; a `packages.config` file or non-SDK project is not itself a defect.

| Mechanism | Purpose and conditional default | When to omit or keep local | Discovery, precedence, and compatibility | How to check; maintenance cost |
| --- | --- | --- | --- | --- |
| `global.json` | Coordinate a compatible .NET **SDK** version and roll-forward across machines when SDK variation matters. | Omit when using the latest compatible installed SDK is intentional; does not select the .NET runtime or standalone Visual Studio MSBuild. | The .NET CLI searches upward from its **working directory**; a specified SDK version follows SDK matching and roll-forward rules. | Run `dotnet --version` in the intended working directory and `dotnet --list-sdks`; keep the selected SDK supported and available in CI. |
| `Directory.Build.props` | Early defaults genuinely shared by several MSBuild projects. | One project-specific setting belongs in its project file; avoid unnecessary shared abstractions. | MSBuild searches upward from the **project directory** and ordinarily imports the first match early; explicit import can combine levels. Applies to compatible SDK and traditional MSBuild projects. | Evaluate properties and preprocess imports; imported defaults can be overridden later. Shared values affect all descendants, so review scope. |
| `Directory.Build.targets` | Shared later targets or settings needing late evaluation. | No late target/import customization is required. | Imported later than project definitions through MSBuild's common targets path; other imports and target hooks can still affect results. Case-sensitive on case-sensitive filesystems. | Inspect preprocessed project/target execution. Late overrides and custom targets increase build coupling. |
| `Directory.Packages.props` | Central Package Management (CPM) where several **PackageReference** projects benefit from shared versions. | Small independent projects, or projects still using `packages.config`. | NuGet automatically selects the nearest such file for a project; parent files need explicit imports when layered. Client/version support matters. | Inspect resolved package versions for each relevant TFM and project. Central changes can affect many consumers. |
| `nuget.config` | Repository-controlled package sources, source mapping, audit sources, and restore options when needed. | Inherited sources/settings are already appropriate; do not add a file just to restate defaults. | NuGet combines machine, user, and repository/solution context; nearer configuration and `<clear />` affect individual sections. Explicit config-file arguments can alter the search. | Inspect effective sources and restore behavior under CI and local identities. Private feeds require credential upkeep; **never commit secrets**. |
| `packages.lock.json` | Persist resolved PackageReference dependency closure when controlled application restores matter. | Do not universally commit for shared libraries, unsupported legacy formats, or projects where it adds little value. | NuGet honors an existing lock file; locked mode rejects input/lock mismatches. SDK/TFM/RID and other restore inputs matter. | Restore in locked mode on a compatible client and review intentional lock-file updates. Maintain the file when dependencies change. |
| Project-level MSBuild properties | Own `TargetFramework(s)`, `RuntimeIdentifier(s)`, output type, conditional references, and project-specific build behavior. | Move only genuinely shared defaults into an appropriately scoped import. | Later MSBuild assignments may override early defaults; global command-line properties and conditions affect effective values. | Evaluate per project, configuration, TFM, and RID. Scattered overrides require explicit review. |
| `.editorconfig` | Tracked C# style/preferences; **STD-007 requires an applicable one for newly established C# projects**. | Do not duplicate an inherited tracked file in every project folder. Existing projects should migrate incrementally. | EditorConfig sections apply by path and hierarchy. Editor/IDE hints are not automatically build-enforced diagnostics. | Inspect effective rules and actual supported analyzer/format checks; maintain coordinated C# conventions under [STD-008](standards/csharp.md#std-008). |
| Solution-level configuration | Group projects and define solution build/platform selection where useful. | A standalone project does not need a solution just to compile. | Solution configuration influences selected projects and configurations; it does **not** govern `Directory.Build.props` discovery. Build tool/solution format support varies. | Inspect selected configuration/platform and build output; avoid needless solution-filter or platform matrix complexity. |
| Repository-owned build/validation scripts | Consistent multi-step validation with local/CI parity when it adds value. | A simple native command already provides a clear, repeatable check. | Scripts run in their specified shell and working directory; availability of SDK, MSBuild, NuGet, secrets and OS is not implied. | Run the script locally and from CI when introduced, record versions/results; script maintenance and cross-platform dependencies are real costs. |

The matrix distinguishes **suggestions** from existing playbook requirements. Do not copy all ten mechanisms into a project automatically. For MSBuild, see [customize by directory](https://learn.microsoft.com/en-us/visualstudio/msbuild/customize-by-directory), [evaluation](https://learn.microsoft.com/en-us/visualstudio/msbuild/evaluate-items-and-properties), and the [MSBuild command-line reference](https://learn.microsoft.com/en-us/visualstudio/msbuild/msbuild-command-line-reference). For NuGet configuration, see [configuration inheritance](https://learn.microsoft.com/en-us/nuget/consume-packages/configuring-nuget-behavior) and the [config-file reference](https://learn.microsoft.com/en-us/nuget/reference/nuget-config-file).

## SDK resolution, targeting, and tooling

The **SDK used to build**, the **target framework selected by the project**, and the **runtime available to execute** the result are different decisions. `global.json` constrains SDK discovery, not an application's runtime roll-forward. Without a matching SDK declaration, the .NET CLI generally uses the highest eligible installed SDK; when a version is declared without a roll-forward option, SDK selection uses the documented default `patch` policy. Explicit choices such as `latestFeature` can reduce unnecessary exact-feature-band constraints, but must fit the supported toolchain. Strict `disable` can be warranted when an SDK-dependent implicit restore graph must remain fixed; it also obliges local and CI environments to install that specific SDK. Record that tradeoff instead of requiring it universally. The SDK search starts from the CLI's working directory, which need not be the project's directory. See [global.json](https://learn.microsoft.com/en-us/dotnet/core/tools/global-json) and [.NET version selection](https://learn.microsoft.com/en-us/dotnet/core/versions/selection).

| Project context | Restore/build starting point | Preconditions and limits |
| --- | --- | --- |
| Modern SDK-style .NET application or library | `dotnet restore`, then `dotnet build --no-restore` when separate evidence is desired. | Compatible supported SDK, TFM, workloads, native dependencies, and relevant OS-specific targets must be available. |
| SDK-style project targeting .NET Framework | Compatible SDK/MSBuild, with .NET Framework reference assemblies and any project-specific tools. | Compile feasibility is not runtime portability; assess Windows APIs, WindowsDesktop targets, COM/native dependencies, and deployment separately. |
| Traditional non-SDK .NET Framework using PackageReference | On a supported Windows toolchain, `msbuild -t:Restore`, then `msbuild`. | Verify Visual Studio Build Tools/MSBuild version, targeting/developer packs, legacy imports, tasks, and custom targets. |
| Traditional non-SDK .NET Framework using packages.config | `nuget restore <solution.sln>` (NuGet CLI), then compatible `msbuild <solution.sln>`. | MSBuild 16.5+ also documents `-t:Restore -p:RestorePackagesConfig=true` for packages.config; prerequisites still apply. |
| Mixed solution | Select restore and build routes **for every included project system**; coordinate compatible tools and OS. | One unsupported project or Windows-specific task can constrain the entire solution. A successful single-project CLI build does not verify the mixed solution. |

The [.NET SDK project overview](https://learn.microsoft.com/en-us/dotnet/core/project-sdk/overview), [MSBuild overview](https://learn.microsoft.com/en-us/visualstudio/msbuild/msbuild), [NuGet restore reference](https://learn.microsoft.com/en-us/nuget/consume-packages/package-restore), and [.NET Framework reference assemblies](https://learn.microsoft.com/en-us/dotnet/framework/migration-guide/reference-assemblies) establish these tooling differences. Older project types and package installation semantics require individual evaluation. Do not assume that installation of a current .NET SDK makes a traditional .NET Framework build run on Linux/macOS, or that successful cross-OS compilation proves the resulting program runs there.

### Target frameworks and runtime identifiers

Keep `TargetFramework` or `TargetFrameworks` aligned with supported consumer/runtime compatibility; multi-target only when real consumers need distinct assets. A NuGet package's compatibility and its transitive assets can differ by TFM. Prefer portable, currently supported runtime identifiers (RIDs) for deployment-specific restoration or publishing; do not add `RuntimeIdentifiers` to every project. `RuntimeIdentifier` and `RuntimeIdentifiers` affect restore assets, output and/or publish requirements, and the actual portable RID graph may change across SDK versions. A generic library build is not evidence of successful `win-x64`, `linux-x64`, or `osx-x64` publishing, native AOT, or execution. See [target frameworks](https://learn.microsoft.com/en-us/dotnet/standard/frameworks), [RID catalog](https://learn.microsoft.com/en-us/dotnet/core/rid-catalog), and [SDK MSBuild properties](https://learn.microsoft.com/en-us/dotnet/core/project-sdk/msbuild-props).

## MSBuild evaluation, imports, and warnings

MSBuild evaluates conditions, properties, items, and imports before executing targets. `Directory.Build.props` is imported early; later project values can override these defaults. `Directory.Build.targets` is imported later and is for legitimate late configuration/targets, not a requirement in every repo. MSBuild searches for these names upward from each **project** directory, not the solution's directory, and ordinarily stops at the first match. To combine nested files, import the intended parent explicitly. On case-sensitive hosts, the filenames' casing matters. Command-line global property assignments generally override project/environment definitions; environment properties are not a reliable substitute for explicit repository policy. See [directory customization](https://learn.microsoft.com/en-us/visualstudio/msbuild/customize-by-directory), [properties and items](https://learn.microsoft.com/en-us/visualstudio/msbuild/comparing-properties-and-items), and [command-line properties](https://learn.microsoft.com/en-us/visualstudio/msbuild/how-to-build-the-same-source-files-with-different-options).

Examples of **illustrative diagnostics**, not actions performed by the playbook:

```text
# Requires a compatible recent .NET SDK/MSBuild for -getProperty
dotnet msbuild MyProject.csproj -getProperty:TargetFramework

# For a traditional project, use a compatible installed MSBuild
msbuild MyProject.csproj -getProperty:Configuration

# Review the evaluated imports/order; the output file is diagnostic
msbuild MyProject.csproj -preprocess:preprocessed.xml
```

Evaluate the property in the appropriate Configuration, TFM/RID, working directory, and toolchain; different evaluations may produce different values. An evaluated property alone does not prove a complete target ran successfully. Do not commit temporary preprocessing output merely to establish standards compliance.

For C#, keep language, nullability, warning, and analyzer configuration compatible with the compiler/TFM. [STD-006](standards/csharp.md#std-006) owns new-project nullable obligations; [STD-007](standards/csharp.md#std-007) owns tracked EditorConfig; [STD-008](standards/csharp.md#std-008) owns selective compiler/CA/IDE diagnostic enforcement. An EditorConfig suggestion is not a passing CI gate. Neither `TreatWarningsAsErrors` nor `AnalysisMode=All` is a universal requirement. For legacy non-SDK projects, confirm availability and activation of compatible analyzers rather than copying properties intended for modern SDK builds. See the [C# guidance map](csharp-guidance.md#compiler-ca-and-ide-diagnostics).

## Dependency ownership and version selection

`PackageReference` represents declared top-level package dependencies in the project file; NuGet resolves their transitive closure at restore. Direct/transitive conflict rules, nearest-minimum resolution, and version ranges can yield a version different from a casual reading of the requested version. In ordinary PackageReference syntax, a bare numeric version is a minimum version, not a universally guaranteed exact pin. Floating versions make the resolved graph more sensitive to new package publication. Inspect what resolved; do not assume the project text fully enumerates runtime packages. Conditional PackageReference entries may vary by target framework or other MSBuild conditions. Asset metadata such as `PrivateAssets` affects what flows to consumers. See [PackageReference](https://learn.microsoft.com/en-us/nuget/consume-packages/package-references-in-project-files) and [NuGet dependency resolution](https://learn.microsoft.com/en-us/nuget/concepts/dependency-resolution).

In `packages.config`, the installed package graph appears as a flat list and package installation may modify project/config files. It is not interchangeable with PackageReference; migrations can lose behavior tied to install scripts, content, and transforms. Preserve a working legacy format until migration has clear value and the package/project compatibility risks are verified. See [packages.config](https://learn.microsoft.com/en-us/nuget/reference/packages-config) and [migration guidance](https://learn.microsoft.com/en-us/nuget/reference/migrate-packages-config-to-package-reference).

### Central Package Management is a choice, not a requirement

If several PackageReference projects share versions, `Directory.Packages.props` can reduce drift. Enable `ManagePackageVersionsCentrally`, define centrally selected `PackageVersion` items, and generally omit `Version` on matching project PackageReference entries. Conditional central versions can accommodate older TFMs. The closest `Directory.Packages.props` is the one automatically discovered; explicit imports are necessary for deliberate hierarchical composition. `VersionOverride` can override central versions where enabled. Optional transitive pinning changes resolution and can affect a packed library's exposed dependencies; review it especially carefully for libraries. Older clients and `packages.config` are not automatically covered. See [NuGet Central Package Management](https://learn.microsoft.com/en-us/nuget/consume-packages/central-package-management).

Consider CPM when there is meaningful multi-project coordination or a shared version-update workflow. For one small independent project, project-local versions are often clearer. Do not introduce `GlobalPackageReference`, transitive pinning, or conditional central layers just because they are available.

## Dependency locking and restore reproducibility

For PackageReference projects, a lock file captures a resolved dependency graph and package content hashes. It can stabilize restoration in the presence of ranges, floating versions, or changing package feeds, but it is **not a complete reproducible-build guarantee**. The selected SDK, project/central dependencies, TFM, RID, sources, compiler, build tasks, environment, and generated assets still matter. NuGet's lock feature has client-version requirements and is not a universal replacement for traditional packages.config restoration.

- **Executable applications:** When controlled restoration matters, generally commit the app's lock file and use locked mode in CI/release verification. This follows NuGet's guidance for an executable at the root of its dependency graph.
- **Shared libraries:** A library's own lock file does not constrain the downstream consuming application's closure. NuGet generally advises against checking in common-code library lock files; a special-purpose library test/release workflow may have its own documented reason.
- **Updating dependencies:** Make intentional package/TFM/RID changes, regenerate and review the lock file with a compatible restore, and then re-enable locked mode. Do not silently accept changed graphs in a controlled CI restore.

Illustrative commands for a compatible **PackageReference** project with lock-file support:

```text
dotnet restore MyApp.csproj --use-lock-file
dotnet restore MyApp.csproj --locked-mode

# Equivalent MSBuild restore property for compatible projects
msbuild MyApp.csproj -t:Restore -p:RestoreLockedMode=true
```

An existing lock file also activates lock-file behavior on restore. Locked mode fails if relevant project dependency definitions and the lock do not agree. Some SDK versions change implicit restore inputs; pinning a specific SDK can be necessary in that identified case, at the cost of exact-SDK provisioning. Review [NuGet dependency locking](https://learn.microsoft.com/en-us/nuget/consume-packages/package-references-in-project-files#locking-dependencies) and [NU1004](https://learn.microsoft.com/en-us/nuget/reference/errors-and-warnings/nu1004) for version-aware diagnostics. A lock-file match does not independently attest the trustworthiness of the feed or reproduce the compiled binary byte-for-byte.

## Package feeds, credentials, auditing, and updates

NuGet accumulates configuration from machine/user/repository contexts. For a repository that requires an explicit allowed-source set, a tracked `nuget.config` with selective `<clear />` and named HTTPS feeds can make restoration more understandable. Review effective source selection in the real working directory; don't assume user-level sources disappear without an explicit clearing policy. **Do not commit package-source credentials, tokens, or personal certificate secrets.** Use supported credential providers or appropriately secured CI/user credentials. Remember that environment-variable credentials may take precedence over configuration entries and complicate diagnosis if stale. See [NuGet configuration](https://learn.microsoft.com/en-us/nuget/consume-packages/configuring-nuget-behavior) and [authenticated feeds](https://learn.microsoft.com/en-us/nuget/consume-packages/consuming-packages-authenticated-feeds).

When several public/private sources can serve similar package IDs, [Package Source Mapping](https://learn.microsoft.com/en-us/nuget/consume-packages/package-source-mapping) can restrict which feeds NuGet **downloads** each package from. Adoption requires supported NuGet clients and mappings that cover all resolved packages, including transitives. Older tooling may ignore mapping. Global package caches can hide the source used for a restore; other NuGet metadata/query commands may still contact unmapped sources. Mapping is a meaningful control for multi-source risk, not proof that a package is safe, signed, or reproducible. Avoid making it mandatory for every single trusted-source repository.

Use the version-compatible built-in [NuGet package auditing](https://learn.microsoft.com/en-us/nuget/concepts/auditing-packages) where available and inspect `NU190x` results. The default direct/transitive audit scope and warning behavior have changed across .NET SDK versions; the PackageReference `NuGetAuditMode` setting does not apply to `packages.config` projects. If treating warnings as errors, explicitly reason about vulnerability-warning policy rather than blanket suppression. Missing advisory data or an unavailable scanner is **unknown coverage**, not a clean security result. Built-in audit and source mapping do not replace supply-chain threat assessment.

Establish a proportionate dependency-update workflow: inspect direct and transitive changes, release notes, compatibility, vulnerable advisories, lock-file changes, tests, and rollback path. Tools such as [Dependabot version updates](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-version-updates) can propose routine updates; [Dependabot security updates](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-security-updates) address known vulnerabilities, with separate grouping behavior. Review PRs instead of silently upgrading or mandating a cadence. Broader supply-chain, SAST/SCA, secrets, security controls, and remediation obligations belong to [Issue #8](https://github.com/infoconex/dotnet-project-playbook/issues/8), not a competing standard introduced here.

## Determinism, CI, and artifact provenance

Deterministic compilation means the compiler can produce identical output from the **same compilation inputs** under its documented conditions. It is narrower than a fully reproducible product artifact. `ContinuousIntegrationBuild=true` configures useful official-build behavior such as source-path normalization; enabling path normalization on developer builds can impair local debugging. Source Link and repository commit metadata can improve .NET package debugging and provenance when the project/toolchain supports them. Do not equate a property value, lock file, or embedded commit with verification that a published artifact was produced securely from the stated revision. See [C# deterministic compilation](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-options/code-generation), [SDK build properties](https://learn.microsoft.com/en-us/dotnet/core/project-sdk/msbuild-props#continuousintegrationbuild), and [Source Link](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/sourcelink).

The existing [CI/local parity standard (STD-002)](standards/engineering-principles.md#std-002) recommends repository-controlled checks called by CI when CI exists. If the project's checks are simple native commands, a wrapper script adds no inherent value. When a repeated multi-step pipeline justifies a script, record the shell and tool versions, working directories, environment variables, conditional platforms, outputs, and actual results. CI may select OS and tools and publish artifacts without duplicating the underlying verification logic. Passing CI on Windows does not establish Linux or macOS behavior; one release configuration does not establish every TFM/RID. No CI or build validator is shipped by this guide.

## Profiles: apply only what matters

| Project profile | Proportionate starting point | Conditional additions and evidence |
| --- | --- | --- |
| New pure C# library | Compatible SDK-style project and applicable tracked EditorConfig (STD-007); explicit needed PackageReferences; tests for behavior under STD-001. | Multiple TFMs only for real consumers; CPM only with useful multi-project sharing; a library lock file is not a consumer-closure guarantee. |
| New CLI application | Project configuration for supported TFM/OS and tracked EditorConfig; ordinary PackageReferences. | App lock file and locked CI restore when graph control matters; RID-specific publish verification when promised. |
| New Web API | Minimal supported SDK project and relevant hosting/deployment settings. | Trusted private feeds, CI/provenance, source mapping and app locks when warranted; verify deployment/platform support independently. |
| New worker | Minimal supported SDK project and relevant process/deployment settings. | Select dependency locks, CI, RIDs and package-source policy according to actual operating environment; no universal web configuration. |
| Traditional .NET Framework project | Preserve compatible non-SDK MSBuild, targeting pack, C# language version, and packages.config/PackageReference mechanisms. | Introduce central props only when supported; do not force a language, package-format, OS or SDK migration solely to adopt the playbook. |
| Mixed or incremental-modernization repository | Inventory each project system, tools, package format, target, source, and CI path. | Choose version-compatible shared files only for eligible subsets; stage migration and validate restore/build/test behavior per affected project. |

### New-project proposal versus existing-repository assessment

For **new projects**, infer obvious defaults from purpose, type, target OS, expected consumers, and known constraints. Propose the minimal file set and explain any extra config's reason; do not administer a configuration questionnaire unless one missing answer changes the outcome. Apply the playbook's existing [C#](standards/csharp.md), [testing](standards/testing.md), and [engineering](standards/engineering-principles.md) obligations as applicable.

For **existing repositories**, inspect the actual solution and project XML, nested `Directory.Build.*` and `Directory.Packages.props`, `global.json`, `nuget.config`, lock files, `packages.config`, `.editorconfig`, workflows/scripts, local tooling assumptions, and documented deliberate exceptions. Record what is **observed**, what is **inferred**, and what is **unknown**. Evaluate incremental change and rollback; avoid recasting every legacy setting as defective. Follow the [AI-assisted start-here workflow](../start-here.md) and preserve the target repository's authorization boundary.

## Illustrative verification and evidence limits

These commands are **examples to run in a consumer repository**, not tests executed by the playbook. Substitute real paths and versions. Select only commands supported by the project system and installed toolchain; run them in the intended working directory.

| Question | Illustrative command or review | Prerequisite and what it does **not** establish |
| --- | --- | --- |
| Which SDK was selected? | `dotnet --info`; `dotnet --list-sdks`; `dotnet --version` | Run from the correct working directory; this does not prove any project builds. |
| What is the evaluated MSBuild property? | `dotnet msbuild MyProject.csproj -getProperty:TargetFramework` | Requires compatible recent SDK/MSBuild and correct conditions. Property evaluation is not execution success. |
| What actually imported a property? | `msbuild MyProject.csproj -preprocess:preprocessed.xml` | Compatible MSBuild and project imports required; inspect preprocessed output, not just file existence. |
| What resolved for PackageReference? | `dotnet restore MyProject.csproj` and inspect output/assets | Compatible SDK project/restore client and source access required. Restore success does not prove runtime behavior or package trust. |
| Is a tracked lock consistent? | `dotnet restore MyApp.csproj --locked-mode` | Only where the NuGet lock feature is supported and a lock exists. A pass is not a reproducible-build attestation. |
| Can a traditional packages.config solution restore? | `nuget restore Legacy.sln` | Compatible NuGet CLI, accessible feeds and legacy solution; no compilation is established. |
| Can a traditional project compile? | `msbuild Legacy.sln -p:Configuration=Release` | Supported MSBuild/Build Tools and necessary targeting packs/tasks; Windows may be required. Run actual tests separately. |
| Were supported warning gates exercised? | Inspect compiler/CA/IDE diagnostics from the actual build and configured tooling | Rule activation, tool versions, and severity differ; EditorConfig alone proves no CI enforcement. |
| Was dependency vulnerability data checked? | Inspect NuGet auditing diagnostics during compatible restore; run version-appropriate package inventory/audit tooling where available | Advisory availability and audit scope differ; packages.config may need a different approach. No warning is not proof of safety. |
| Does CI match local checks? | Compare exact invoked commands, scripts, tool versions, OS, TFM/RID, and results | One environment's success cannot establish others; skipped or unavailable checks are gaps. |

Document **planned** commands separately from **observed** ones. For each verified claim, record repository revision/commit, tool versions, OS, inputs, invocation, meaningful output/results, and known limitations. Authoritative documentation supports a **Documented** claim about platform behavior; only actual execution supports a **Verified** claim for the particular repository/environment. A targeted experiment is useful only when material uncertainty remains after authoritative research. This follows the [research-first and evidence-based engineering principles](standards/engineering-principles.md#evidence-based-technical-decisions).
